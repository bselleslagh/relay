01 / OPEN WEARABLES

Give your data a home.

Open Wearables is the separate, open-source platform that receives and stores your data. Relay’s current integration was reviewed against version 0.9.0; the examples here pin that version, rather than assuming a future release is compatible.

Try the platform on your computer

Install Docker with Compose and Git. Start Docker, then open a terminal:

Terminal · initial setup
git clone --branch 0.9.0 --depth 1 https://github.com/the-momentum/open-wearables.git
cd open-wearables
cp backend/config/.env.example backend/config/.env
cp frontend/.env.example frontend/.env

Before starting, edit backend/config/.env: set your ADMIN_EMAIL, a unique ADMIN_PASSWORD, and a random SECRET_KEY. You can generate a secret with openssl rand -hex 32. Keep these values private. The admin password is seeded on the first start; changing the file later does not reset an existing account.

Terminal · start and check
docker compose up -d
docker compose ps
curl -fsS http://localhost:8000/openapi.json > /dev/null && echo "API ready"

Open localhost:3000 on that computer and sign in with the admin details you chose. The developer portal runs on port 3000; the API runs on port 8000. Confirm the services are running before proceeding.

For real health data, deploy a protected server

The repository’s Compose file is a development setup with default database credentials and exposed service ports. Use the official production deployment guide before syncing personal data: pin the backend and frontend images to an exact release, set production secrets, keep databases private, and configure backups and HTTPS.

Make the API reachable from your iPhone

Use an HTTPS address with a certificate trusted by iOS, such as https://health.example.com, routing to the API. Configure the portal’s API URL and allowed origins for your deployment. A private VPN is also an option if both devices can reach the server and HTTPS remains valid.

localhost on your iPhone means the iPhone itself. Use the server’s reachable API address in Relay, not the portal URL or a path ending in /api/v1. Keep any required port. Open the API’s /docs page in iPhone Safari to check networking and certificate trust.

02 / RELAY

Connect your iPhone.

  1. Install Relay. During the beta, install TestFlight and accept your Relay invitation. You need iOS 26 or later. Developers can also build Relay from source.
  2. Create your Open Wearables user. In the developer portal, open Users and create or select your personal user. This health-data profile is separate from the administrator account.
  3. Generate an invitation code. On that user’s page, generate a one-time invitation code. In Relay, tap Connect your server, enter the HTTPS API address and the code, then tap Connect securely. Use the code while it is valid.
  4. Choose Apple Health access. Allow the categories you want to sync. Relay requests read access only. Your administrator password and server API key do not belong in Relay.
  5. Run your first sync. Keep Relay open, tap Sync now, and wait for the initial import. Then check that records appear under the correct user in Open Wearables.

30 days to start

The first import and manual rescans cover the last 30 days. Later syncs pick up new records. Older records already on the server stay there.

Background, when iOS allows

Automatic sync depends on iOS scheduling and connectivity. It is not a continuous, real-time feed. Use Sync now when you need a fresh reading.

Relay does not export every HealthKit type. Deleting a record in Apple Health does not currently delete its server copy. See coverage and limitations and the privacy policy.

03 / YOUR AI CLIENT

Put your model in the loop.

MCP is a standard way for an AI client to call tools. Open Wearables supplies tools for looking up users, activity, sleep, workouts and individual measurements. The model runs in your chosen client; it does not run inside Relay.

Install the official MCP adapter

On the computer running your AI client, install uv (0.9.17 or newer) and Git. Then:

Terminal · on your AI computer
git clone --branch 0.9.0 --depth 1 https://github.com/the-momentum/open-wearables.git open-wearables-agent
uv sync --frozen --project open-wearables-agent/mcp
cd open-wearables-agent/mcp
pwd
command -v uv

Save the two paths printed at the end. In the Open Wearables portal, create an API key under Settings → Credentials. Keep it in your AI client’s private configuration, never in a chat prompt or public repository.

Two different credentials

Relay uses a one-time pairing code and user-scoped tokens. The MCP adapter uses a server API key. In Open Wearables 0.9.0, general API keys have broader access than one user or read-only queries. Use a server containing only data you intend this client to access; a prompt asking for one user is not an access-control boundary.

Add this MCP configuration

Replace the command path, adapter directory, API address and API key. Merge the open-wearables entry into your existing mcpServers object if you already have other servers configured.

mcp.json · replace the placeholders
{
  "mcpServers": {
    "open-wearables": {
      "command": "/ABSOLUTE/PATH/TO/uv",
      "args": [
        "run", "--frozen", "--directory",
        "/ABSOLUTE/PATH/open-wearables-agent/mcp", "start"
      ],
      "env": {
        "OPEN_WEARABLES_API_URL": "https://health.example.com",
        "OPEN_WEARABLES_API_KEY": "YOUR_OPEN_WEARABLES_API_KEY",
        "LOG_LEVEL": "WARNING"
      }
    }
  }
}

Reload the MCP server or restart the client, then inspect its tools. You should see get_users, get_activity_summary, get_sleep_summary, get_workout_events and get_timeseries.

The API URL is not an HTTP MCP endpoint. This adapter is a local process launched by the client, and it calls your remote server’s REST API. An AI client that accepts only remote MCP URLs cannot use this configuration directly.

04 / MAKE IT USEFUL

Start with one small question.

First ask the client to list users with get_users and confirm your user ID. Then try a short, explicit time range:

TRY ASKING
For my selected user ID, compare my sleep duration over the last 7 complete days. Use the Open Wearables tools. Show dates, timezone, units and source coverage. Tell me which days are missing, and don’t treat missing records as zero.

Compare the answer with a few records in the portal. Ask for descriptive patterns before broad conclusions. Tool results can be incomplete; check date ranges, pagination and overlapping device sources. The 0.9.0 adapter has query limits, so split large requests into smaller periods.

This setup helps you explore personal records. Model-generated observations can be wrong and are not a diagnosis.

WHEN SOMETHING DOESN’T CONNECT

A few things to check.

Relay cannot reach my server

Check the API address in iPhone Safari, HTTPS certificate trust, VPN connectivity and the reverse proxy. A portal on port 3000 is not the API on port 8000. Do not use your computer’s localhost address on the phone.

The invitation code fails

Generate a fresh code for the intended user. Codes are single-use and expire. Enter the invitation code in Relay, not an administrator password or MCP API key.

The sync succeeds, but data is missing

Check the correct user, supported data types, Health permissions and the 30-day import window. iOS does not tell Relay which read permissions you denied. After changing access in Health, use Relay’s Settings → History → Rescan last 30 days.

My AI client cannot start the MCP server

Use absolute paths for uv and the MCP directory. Check that uv is installed for the same OS/user as the client, dependencies installed successfully, and the client supports stdio MCP. Read its MCP logs for startup errors.

The tools return an authentication error or no records

Use a valid Open Wearables API key, the API base URL without /api/v1, and a network route from the AI computer to the server. Confirm the user ID, date range and completed phone sync. An AI provider’s API key cannot authenticate to Open Wearables.

My model answers without fetching data

Enable the MCP tools in the chat and choose a model that handles tool calls. Ask it to call get_users explicitly and inspect the tool result. If the model cannot use tools reliably, switch models instead of trusting invented health summaries.
